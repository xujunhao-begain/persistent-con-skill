# 远端操作约束与风险闸门

本文件是技能的**操作红线手册**：哪些远端操作必须先取得用户同意、哪些无论如何都不许由
agent 自行发起、以及闸门在代码层面是怎么强制的。SKILL.md 里是精简协议，细节看这里。

## 为什么要有闸门

持久会话的能力面很大：一旦登录成功，agent 就握着一个**生产环境的 shell**，
后续每条命令都不再需要密码。这带来两个特有风险：

1. **越权范围扩散**——用户只想"看一眼日志"，但同一个会话里也能删库、停服务、改防火墙。
2. **不可回滚**——远端没有回收站、没有撤销键；`rm` 删掉就是删掉，服务停了就是线上故障。

所以技能不靠"记得小心"，而是把约束**写进唯一的出口**：所有发往远端的内容都必须经过
`send.sh`，而 `send.sh` 在写入会话管道之前强制调用 `risk_check.py` 分级。

## 三级风险与放行条件

| 等级 | 含义 | 放行条件 | send.sh 退出码 |
|---|---|---|---|
| `SAFE` | 只读/无害（`ls`/`ps`/`df`/`tail`/`systemctl status`…） | 直接放行 | 0 |
| `CONFIRM` | 破坏性但常规（删文件、停服务、改配置、装包、动数据库…） | **必须先取得用户明确同意**，再带 `-y` 重发 | 拒发 = 3 |
| `BLOCK` | 灾难性 / 不可回滚 / 规避审计（`rm -rf /`、格式化、重启主机、清 history…） | agent **一律不得自行发起**；仅当用户亲口指定该命令时，带 `-y --force-dangerous` | 拒发 = 4 |

闸门自身报错（配置坏、脚本异常）时 **fail closed**——不发送，退出码 2。

规则全目录随时可查：

```bash
python3 "$SK/scripts/risk_check.py" --list
```

单条命令预演（不发送，只看判级）：

```bash
python3 "$SK/scripts/risk_check.py" 'systemctl restart nginx'
```

## agent 必须遵守的行为约束

### 1. CONFIRM 级：先讲清楚，再动手

拿到 `RISK: CONFIRM` 时，**不要**换个写法绕过、不要拆成几条小命令规避、不要直接补 `-y`。
正确做法是先向用户讲清三件事，拿到明确同意后才带 `-y` 重发：

- **要做什么**：把命令原文贴给用户看（不要只说"清理一下"）。
- **影响什么**：哪台机器、哪个账户、哪些路径/服务/数据、是否会中断线上流量。
- **怎么回滚**：备份在哪、失败了怎么恢复；**没有回滚手段时必须明说**。

用户的同意要落在**这一轮对话**里。"上次你同意过删日志"不能延用到这次删另一个目录；
"你说随便搞"不是对某条具体高危命令的授权。建议同时用 `--note "<用户同意的原话>"`
把授权记进审计日志。

### 2. BLOCK 级：只能由用户发起

BLOCK 是红线，agent 自己想出来的方案里**不应该出现**这类命令。命中时正确的反应是
**提出更安全的替代方案**，而不是申请放行：

| 想做的事 | 别用 | 改用 |
|---|---|---|
| 清理磁盘 | `rm -rf /var/log` | 先 `du -sh /var/log/*` 定位大文件，再逐个确认删除 |
| 让配置生效 | `reboot` | `systemctl reload <svc>`（不行再确认 restart） |
| 改防火墙 | `iptables -F` | 只加/删具体规则，并先确认当前 SSH 来源不受影响 |
| 删一批文件 | `rm -rf $DIR/` | 先 `echo "$DIR"` 确认变量已展开，再用绝对路径 |
| 收拾现场 | `history -c` | 什么都不做——清审计痕迹本身就是不该做的事 |

只有用户**亲口写出那条命令**并确认要执行时，才允许 `-y --force-dangerous`；此时仍要先
复述影响面。

### 3. 只读优先：动手前先看清

- 删之前先 `ls -la` / `du -sh` 看清目标到底是什么、有多大。
- 改文件之前先 `cp x x.bak.$(date +%F)`（备份本身是 SAFE 的）。
- `kill` 之前先 `ps -ef | grep` 确认 pid 属主与命令行，别按名字乱杀。
- 批量同步先 `rsync --dry-run`，确认删除清单再去掉 dry-run。
- 数据库 `DELETE`/`UPDATE` 之前先把同样条件的 `SELECT count(*)` 跑一遍，把行数给用户看。

### 4. 范围约束：不越出用户交代的边界

- **只在用户指定的路径下写**。技能不应主动去改 `/etc`、系统服务单元、别人的 home。
- **切账户要用户明示**（`sudo su -` 已是 CONFIRM 级）。不要为了"方便"提权到 root。
- **不装东西**：生产机上装包/改依赖会影响其它服务，必须用户同意。
- **不碰凭据与持久访问**：`authorized_keys`、`passwd`、`sudoers` 一律先问。

### 5. 长跑任务

- 要部署监听端口的服务，**先确认端口未被占用**（在远端 `ss -tlnp | grep <port>`）；
  端口被占时把情况交给用户挑，不要自己换端口硬起。
- 长跑任务用 `nohup ... &` 脱离会话，并**明确告知用户**："这个进程会在你收工后继续跑，
  pid 是 X，停它的命令是 Y"。留下不告知的常驻进程等于留了个坑。

### 6. 收工要交账

会话里做过的每一次发送都记在 `$SD/audit.log`（时间、风险等级、是否已确认、命令原文，
纯数字密码自动脱敏）。收工时用它给用户一份改动清单：

```bash
cat "$SD/audit.log"                                  # 全量
grep -v 'LEVEL=SAFE' "$SD/audit.log"                 # 只看有副作用的操作
```

汇报里要包含：改了什么、起了/停了什么进程、留了哪些常驻任务、哪些操作没有回滚手段。

## 按环境定制策略

`config.local.json` 里的 `risk_policy` 段（字段见 `config.example.json`）：

```json
"risk_policy": {
  "enabled": true,
  "protected_paths": ["/data/prod", "/opt/app"],
  "block_patterns": ["\\bdrop\\s+database\\b", "\\bdeploy\\.sh\\s+--prod\\b"],
  "confirm_patterns": ["\\bmyctl\\s+(restart|deploy)\\b"],
  "allow_patterns": ["^tail -f /data/app/logs/\\S+$"]
}
```

- `protected_paths`：本环境的关键业务目录。被**整体**删除时按 BLOCK 处理（其下子路径仍是
  CONFIRM），用来防"清理缓存顺手把整个应用目录删了"。
- `block_patterns` / `confirm_patterns`：追加本环境特有的红线与需确认规则（正则，
  对原文与掩码文本各匹配一次，宁可多报）。典型用途是把内部运维脚本纳管，例如
  一条 `deploy.sh --prod` 就该是红线。
- `allow_patterns`：对被规则误伤的已知安全写法做豁免——**整条命令**命中即直接判 SAFE，
  所以务必写得足够窄（用 `^...$` 锚定），否则等于自己开了个后门。
- `enabled: false` 会**整体关闭闸门**，强烈不建议；`check_config.py` 会对此持续告警。

改完配置用 `python3 scripts/check_config.py --skill-dir .` 复核：类型写错、正则非法、
开了豁免口子都会被指出来。

## 闸门覆盖不到的地方（要自己心里有数）

- 直接 `printf ... > "$SD/session.in"` 手写管道会绕过闸门。**不要这么做**：需要发东西
  就走 `send.sh`，否则约束和审计一起失效。
- 闸门看的是**命令文本**。`bash deploy.sh` 里面写了什么它看不见——所以执行来源不明的脚本
  之前，先 `cat` 出来看，必要时把内容给用户过一眼。
- 正则不是解析器，存在漏判可能。闸门是**兜底**，不是免责声明：判断责任仍在 agent 身上。
